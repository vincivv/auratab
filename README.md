# AuraTab

A Chrome (Manifest V3) new-tab-replacement extension. The core idea: widgets
you rearrange the way you rearrange iOS home screen icons — long-press to
enter "jiggle mode," drag them around a grid, resize them, add or remove
them — instead of the settings-panel-based configuration every other new-tab
extension (Bonjourr, Tabliss, Momentum, etc.) uses. No accounts, layout and
preferences stored locally in the browser. The project started as fully
offline-only; that's no longer a hard goal (see below) — a couple of widgets
now call small public APIs for real data, each one a deliberate, documented
choice, not a silent default.

This file is the single place to start. For more depth on any specific
point, follow the links inline rather than reading top-to-bottom.

## Current state

**Built and working:**
- Full MV3 scaffold (Vite + `@crxjs/vite-plugin` + React 19 + TypeScript),
  loads as an unpacked extension and overrides the new tab page.
- A real grid-based layout engine: widgets live on a discrete cell grid, not
  free pixels. Dragging/resizing still feels continuous and spring-driven
  (not janky/discrete) while your pointer is down; on release it snaps to
  the grid, and if you drop onto cells another widget occupies, that widget
  gets pushed out of the way (push-down collision resolution).
- 6 widgets: **Clock**, **Search**, **Quick Links**, **Notes**, **To-Do
  List**, **Weather** — see [Widget catalog](#widget-catalog) below.
- A right-side slide-in Settings drawer: **General** tab (motion/clock
  format/search engine/widget transparency preferences, an explicit "enter
  edit mode" action, "Reset to default layout"), **Widgets** tab (a gallery
  to add widgets, with live previews of each one, click-to-add or
  drag-and-drop onto the canvas), and **Background** tab (see below).
- Persistence via `chrome.storage.local` (a Zustand store, debounced
  writes) — your layout and preferences survive closing the tab.
- A real starter/default layout (not a single placeholder) shown on first
  run and restorable via "Reset to default layout."
- A "liquid glass" visual style — translucent, blurred, bordered cards for
  most widgets; Clock and Search render "chromeless" instead, floating
  directly on the canvas with no card, closer to how a phone's lock-screen
  clock looks. Card transparency (tint alpha + blur) is user-adjustable via
  a slider in Settings > General.
- A background picker (`src/backgrounds/`, Settings > Background) — a
  curated set of static CSS gradient presets, or upload your own image
  (validated, stored as a `Blob` in IndexedDB via `idb`, not in
  `chrome.storage.local`). This is a first, simpler pass, not the spec's
  real generative animated engines — see "Not built yet" below.

**Not built yet** (present in the original spec, still pending):
- The 4 generative animated background engines the spec calls for — still
  the biggest gap between the spec's vision and what's on screen. The
  static gradient presets above are a stopgap, not a substitute.
- Local video background upload — image upload is built (see above); video
  is not, though the size ceiling for it is already reserved (see
  `CLAUDE.md`'s "Upload size ceilings").
- Bundled default background media (photos/videos shipped with the
  extension) — the presets are CSS gradients, not media files.
- A formal performance-profiling pass against the spec's load-time/60fps
  targets.
- Chrome Web Store listing assets and submission.

**Deliberately diverged from the original spec** (each decided explicitly
mid-build, not silently — see `CLAUDE.md` for the full reasoning on each):
- Free pixel placement → a real grid with push-down collision resolution
  (the spec explicitly flagged this as bigger, deferred scope; built anyway
  on request).
- Standalone "+" widget gallery → folded into the Settings drawer.
- 4-widget catalog → 6 (added To-Do List and Weather).
- Zero network calls, no exceptions → **relaxed 2026-07-31, not just a
  widget-level exception anymore**: "fully offline" stopped being a hard
  product goal, per explicit direction. Two features currently call out:
  Weather fetches live conditions once a user adds it and types a city;
  Quick Links fetches real favicons for saved links from Google's public
  favicon endpoint (falling back to an initial-letter tile if that fails).
  Full reasoning and how each was decided: `CLAUDE.md`'s "Network calls"
  entry.

## Quick start

```sh
npm install
npm run dev
```

In Chrome: `chrome://extensions` → enable Developer mode → **Load
unpacked** → select `dist/` (generated by the dev server, hot-reloads as
you edit).

```sh
npm run build       # production build to dist/
npm run typecheck    # tsc -b --noEmit, no emit
```

## Project structure

```
src/
├── App.tsx                    composition root — renders the canvas, all
│                               widgets, and the settings drawer
├── canvas/                    generic drag/resize/edit-mode machinery —
│   │                          knows nothing about specific widget content
│   ├── DraggableBox.tsx       the draggable/resizable/wobbling box itself
│   ├── useDragPhysics.ts      spring-based drag physics (react-spring)
│   ├── gridConfig.ts          DOT_SIZE, px<->cell conversion — single
│   │                          source of truth for grid math
│   ├── gridCollision.ts       push-down collision resolver
│   ├── useEditMode.ts         edit ("jiggle") mode state machine
│   ├── useLongPress.ts        long-press-to-enter-edit-mode gesture
│   ├── WobbleWrapper.tsx      the jiggle rotation animation
│   ├── RemoveBadge.tsx        the × delete control
│   └── clampToViewport.ts     keeps widgets on-screen during drag
├── widgets/                   one folder per widget type
│   ├── types.ts               WidgetDefinition / WidgetInstance contracts
│   ├── registry.ts             the list every widget registers into
│   ├── clock/ search/ links/ notes/ todo/ weather/
│   │   ├── <Name>Widget.tsx    the widget's own React component
│   │   └── <name>Widget.def.ts its WidgetDefinition (size, chromeless?, ...)
├── settings/                  the Settings drawer
│   ├── SettingsPanel.tsx      the slide-in drawer shell + tab switching
│   ├── GeneralTab.tsx         preferences, edit-mode entry, reset-to-default
│   ├── WidgetsTab.tsx         the widget gallery (live previews, add)
│   └── BackgroundTab.tsx      background presets + custom image upload
├── backgrounds/                background picker (presets + custom upload;
│   │                          NOT the spec's generative animated engines)
│   ├── types.ts               BackgroundSelection (preset id | custom)
│   ├── presets.ts             curated static CSS gradients
│   ├── useBackgroundStyle.ts  resolves a BackgroundSelection into CSS
│   └── media/
│       ├── uploadValidation.ts     file type/size checks (~25MB images)
│       └── backgroundMediaStore.ts IndexedDB (via idb) blob storage
├── store/
│   ├── layoutStore.ts         Zustand store — widgets, preferences,
│   │                          collision-aware move/resize/add actions,
│   │                          the default starter layout
│   └── persistence.ts         hydrates from / writes to chrome.storage.local
├── lib/                       small shared utilities (clamp, viewport size,
│                              reduced-motion context)
└── styles/global.css          all styling — no CSS-in-JS/modules
```

## Widget catalog

| Widget | Chrome | Notes |
|---|---|---|
| Clock | chromeless | Live time + date. 12h/24h via preferences. |
| Search | chromeless | Submits to a hardcoded URL template (no `search` permission used). |
| Quick Links | glass card | User-added link tiles; add/remove flow is a plain `window.prompt`, not a polished inline editor. Tile icons are real favicons via Google's public favicon endpoint (a network call — falls back to an initial-letter tile if it fails). |
| Notes | glass card | Widget shows a list of created notes (title/preview/date); "+" or clicking a note opens a full-size editor (title + plain text body, no rich-text toolbar) rendered as an overlay via a React portal. |
| To-Do List | glass card | Checkable items with inline text editing. |
| Weather | glass card | Calls Open-Meteo (free, no API key) to geocode a user-typed city and fetch current conditions. Does nothing until a user adds it and enters a city. |

"Chromeless" vs "glass card" is a flag on the widget's definition
(`chromeless?: boolean`), not a special case in the canvas — see
`CLAUDE.md`'s "Chromeless widgets" entry if adding a widget that should
float on bare canvas rather than sit in a card.

## Key architecture ideas worth knowing before changing things

- **The canvas layer knows nothing about widget content.** `DraggableBox`
  and friends operate purely on `{ id, x, y, w, h }` — adding a new widget
  type never requires touching `src/canvas/`.
- **The grid is pixel-based internally, cell-based at the edges.**
  `DraggableBox` drags/resizes in continuous pixels for a smooth feel; the
  conversion to/from grid cells and the collision-aware store updates
  happen one layer up, in `App.tsx`. Don't reintroduce grid-cell math inside
  `DraggableBox` itself.
- **One shared glass-material CSS class** (`.glass-material` in
  `global.css`) drives both the real on-canvas widget chrome and the
  Settings gallery's live widget previews, so the two visual treatments
  can't silently drift apart.
- **Widget previews in the gallery are the real widget component**, scaled
  down via CSS `transform`, not a hand-drawn icon — what you see in the
  gallery is guaranteed to match what lands on the canvas.

## What's next

Roughly in priority order, picking up where the original spec's milestones
left off:

1. The 4 generative background engines (spec §4.4/§6.5) — this is the
   biggest visible gap between the spec's vision and what's on screen today.
   The spec calls for validating one engine's performance alongside active
   widget dragging *before* building the rest, since background rendering
   competing with drag physics for frame budget is flagged as a real risk.
   The static gradient presets built 2026-08-03 (Settings > Background) are
   a stopgap, not a substitute for this.
2. Local video background upload (spec §6.6) — image upload + IndexedDB
   storage is built; video isn't, though the size ceiling is reserved.
3. Bundled default background media (photos/videos shipped with the
   extension, vs. today's CSS gradient presets).
4. A real performance-profiling pass against the spec's NFR-1 (<150ms load)
   and NFR-2 (60fps drag) targets — not yet formally measured.
5. Store listing assets and submission, once the above are in place.

Smaller open threads: the Quick Links widget's add/edit flow is a rough
`window.prompt`-based placeholder, not a polished inline editor; a few
recently-built interactions (the weather fetch, grid collision push-down,
the background picker's custom image upload) haven't been manually
exercised end-to-end in a loaded browser, only typechecked and built.
